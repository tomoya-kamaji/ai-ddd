# レビューチェックリスト

各フェーズの終わりに使う。項目は「これが崩れているとPhase 4で往復が必要になる」という観点で選んでいる。

## ユースケース分析

- [ ] ユースケースは「アクターが動詞+目的語で行う」粒度で書かれているか（大きすぎないか）
- [ ] 対象スコープと対象外が明言されているか
- [ ] 各ユースケースに事前条件・事後条件があるか
- [ ] 代替フロー・例外フローが最低1つは書かれているか（無ければ理解が浅い可能性が高い）

## ドメイン分析（SUDO: S/O/D）

- [ ] （複数プロダクトに跨る場合）システム関連図で関係者・外部システムの抜け漏れがないか
- [ ] オブジェクト図の具体例は、シナリオ記述の代替/例外フローをカバーしているか
- [ ] オブジェクト図の吹き出しルールが、すべてドメインモデル図のどこかのクラスに責務として割り当てられているか
- [ ] ドメインモデル図に集約範囲（どこまでを同時に整合させるか）が明示されているか
- [ ] 多重度・制約・英語名（対訳）が実装できる粒度まで具体化されているか

## 実装（関数型ドメインモデリング）

- [ ] 制約のある属性は Companion の `create` が `Result` を返す形で、検証済みの値だけがその型になっているか
- [ ] ID は Branded Type で、取り違えがコンパイルエラーになるか
- [ ] 状態は `kind` 判別子の Discriminated Union で、状態固有の属性が必須になっているか
- [ ] 状態遷移関数の引数型が遷移元の状態に制約されているか
- [ ] 集約の内部コレクションを Companion 関数の外から組み替えていないか
- [ ] ドメイン層・ユースケース層で `throw` していないか（`assertNever` を除く）
- [ ] ユースケース関数の中に業務判定（定員・重複・期限など）が書かれていないか
- [ ] Repository が `insert / findById / findByXxx / update` 以外の業務操作を持っていないか
- [ ] `new Date()` をドメイン・ユースケース内で呼んでいないか
- [ ] `as const` / `as const satisfies` 以外の `as` を使っていないか（ID の `of` を除く）
- [ ] ドメインモデル図の吹き出しルールごとに対応するテストがあるか（※サンプル実装ではテスト未実装。実プロジェクトでは必須）

## Phase 4（往復）

- [ ] 実装中に見つかった想定外のケースを、ユースケースのシナリオ記述に書き戻したか
- [ ] 実装中に見つかった不変条件の見落としを、ドメインモデル図の吹き出しに書き戻したか
